## §2. CONFLICT RESOLUTION RULES

When a category has multiple options selected, they are not contradictory — they serve different contexts. Every multi-select resolves via a **context gate**:

### 2.1 Why Multi-Selects Exist

Multi-select preferences fall into three legitimate patterns:

1. **Context-gated** — different options for different screens (e.g., Modal transitions vs Standard transitions)
2. **Tiered intensity** — baseline option + amplified option for special moments (e.g., haptic restraint + premium patterns)
3. **Tool kit** — 2–3 options as available tools, with explicit rules on when to reach for each

### 2.2 Resolution Hierarchy

When in doubt, resolve by:

```
Is the choice already context-gated by category type?
├── Yes (e.g., Standard vs Modal transition) → Use the one matching the situation
└── No (e.g., 3 accent applications)
    ├── Is one option the CP default? → Default to it
    └── None is default → Use the MOST RESTRAINED option as baseline,
                          reserve others for explicit cases (see §5, §15)
```

### 2.3 When No Context Rule Applies

Default to the option closest to Calm Precision 6.4.1's philosophy: less decoration, more restraint, higher signal-to-noise. A design review should catch deviations before they ship.

## §3. MOTION & TRANSITIONS

### 3.1 Screen Transition — Context Map

Three transitions selected, each with a non-overlapping context:

| Context | Transition | When to Use | Spec |
|---------|-----------|-------------|------|
| Connected element (tapped card → detail) | **Hero Expansion** | Tapping a card with a hero image or defining visual element that will anchor the detail view | Tap target expands to fill screen. Shared element transition via `matchedGeometryEffect` or iOS 18 `zoomTransition`. Duration 350ms. |
| Standard push in a stack | **Slide Push** | Any `NavigationLink` that is NOT a visual expansion. Settings detail, list row to form, etc. | Push right-to-left, 300ms ease-out. Previous moves left at 30% speed (parallax). Swipe-back always enabled. |
| Modal layer (sheet, full-screen modal) | **Slide Up** | `.sheet`, `.fullScreenCover`, any "overlay on current context" | Slide up from bottom, 350ms spring (0.7 damping). Scrim to 30% opacity. Swipe-down to dismiss. |

### 3.2 Transition Decision Tree

```
Presenting a new screen?
├── Tapped element has a defining image/shape that belongs on the next screen?
│   └── YES → Hero Expansion (matchedGeometryEffect / zoomTransition)
├── Is the new screen a temporary layer (cancel-able, doesn't change app state)?
│   └── YES → Slide Up (.sheet or .fullScreenCover)
└── Otherwise (drilling deeper into hierarchy)
    └── Slide Push (NavigationStack default)
```

### 3.3 SwiftUI Implementation Notes

**Hero Expansion (iOS 18+):**
```swift
NavigationLink {
    DetailView()
        .navigationTransition(.zoom(sourceID: item.id, in: namespace))
} label: {
    CardView(item: item)
        .matchedTransitionSource(id: item.id, in: namespace)
}
```

For iOS 17 fallback: use `matchedGeometryEffect` with a custom transition.

**Slide Up (Standard Modal):**
```swift
.sheet(isPresented: $showDetail) {
    DetailView()
        .presentationDetents([.medium, .large])
        .presentationDragIndicator(.visible)
        .presentationBackground(.thinMaterial)
}
```

**Slide Push:** Native `NavigationStack` default. No configuration needed.

### 3.4 Pull-to-Refresh — Progress Arc

Single decision: arc draws 0–100% with pull progress. Full circle triggers refresh.

```swift
struct ProgressArcRefresh: View {
    @State private var pullProgress: Double = 0
    @State private var isRefreshing = false

    var body: some View {
        // Custom refresh control replacing default .refreshable spinner
        // Arc path draws based on pullProgress (0.0 to 1.0)
        // At 1.0, switch to continuous rotating spinner
    }
}
```

**Auto-apply:**
- All refreshable lists use the Progress Arc component, not the native gray spinner
- Pull distance to trigger: 60pt (aligns with CP mobile patterns)
- Haptic on trigger (per §7.2 Key Moments rule)

## §4. LIST, CARD & CONTENT PATTERNS

### 4.1 List Item Separator — Context Map

Two styles selected, each with a distinct use case:

| Style | When to Use | Spec |
|-------|-------------|------|
| **Card Per Row** | Feed-style content, each row is independently interactive with metadata hierarchy | 10pt corner radius, `Color(.secondarySystemBackground)` fill. 8–10pt vertical gap. Shadow: only on interactive cards per CP 6.4.1 card interactivity rules. |
| **Inset Hairline** | Dense list content, grouped related items, system-style settings/forms | 0.5pt hairline, inset 16pt from left (below leading icon/avatar). `Color(.separator)` color. No divider after last item. |

### 4.2 Separator Decision Tree

```
Building a list?
├── Are rows independently interactive with their own visual identity?
│   ├── Each row has image/metadata/rich content? → Card Per Row
│   └── Simple text/value rows? → Inset Hairline
├── Is this a settings, form, or configuration list?
│   └── YES → Inset Hairline (matches iOS system lists)
├── Is this a content feed (news, activity, messages)?
│   └── YES → Card Per Row
└── Is this grouped related data (transaction list, same-day items)?
    └── Inset Hairline with `Section { }` grouping
```

### 4.3 Important CP Intersection

Per Calm Precision core Principle 1 (Group, Don't Isolate): **never put individual borders/shadows on every row if they form a logical group.** Card Per Row is allowed only when rows are genuinely independent items (each is its own entity/event), not when they form a group of related settings or data.

**Test before choosing Card Per Row:** Would the user scan these rows as one logical unit? If yes → Inset Hairline. If they'd tap one and move to another context → Card Per Row.

### 4.4 Card Per Row SwiftUI Pattern

```swift
ScrollView {
    LazyVStack(spacing: 10) {
        ForEach(items) { item in
            CardRow(item: item)
                .padding(16)
                .background(Color(.secondarySystemBackground))
                .clipShape(RoundedRectangle(cornerRadius: 10))
        }
    }
    .padding(.horizontal)
}
```

### 4.5 Inset Hairline SwiftUI Pattern

```swift
List {
    Section {
        ForEach(items) { item in
            Row(item: item)
        }
    }
}
.listStyle(.insetGrouped)  // iOS default — already inset hairline
```

## §5. SURFACE, COLOR & DEPTH

### 5.1 Gradient Usage — Tiered Intensity

Three gradient options selected, tiered by expressiveness:

| Tier | Gradient | When to Use | Risk |
|------|----------|-------------|------|
| Baseline | **Linear Gradient** | Buttons, small surfaces that need subtle depth | Low — adds dimensionality without visual noise |
| Premium moment | **Mesh / Aurora Gradient** | Hero surfaces (splash, onboarding hero, premium badge), one per screen maximum | Medium — can dominate if overused |
| Brand moment | **Duotone Wash** | Section headers, featured cards, editorial content blocks | Medium — reserve for moments of brand expression |

### 5.2 Gradient Decision Tree

```
Need depth on a surface?
├── Small element (button, metric pill)?
│   └── Linear gradient — 2-3% brightness shift, subtle
├── Hero/feature surface (splash, onboarding, premium)?
│   ├── One per screen? → Mesh / Aurora Gradient
│   └── Already have one? → Solid color (don't stack aurora)
├── Editorial or brand-expressive block?
│   └── Duotone Wash
└── Standard card or row?
    └── NO GRADIENT — solid surface color (per CP signal-to-noise)
```

### 5.3 Mesh Gradient Caution

`MeshGradient` requires iOS 18+. Provide fallback:

```swift
if #available(iOS 18.0, *) {
    MeshGradient(
        width: 3, height: 3,
        points: [...],
        colors: [...]
    )
} else {
    LinearGradient(colors: [...], startPoint: .topLeading, endPoint: .bottomTrailing)
}
```

**Audit flag:** Per your Calm Precision memory, Aurora themes have unresolved mobile degradation guidance (particularly backdrop-filter blur on older devices). Mesh gradients are in the same family and share this risk. Test on older iPhones (SE, iPhone 11) for perceptible performance drop.

### 5.4 Dark Mode Surface Treatment — Context Map

Three surface treatments selected, each for a different content context:

| Context | Treatment | When |
|---------|-----------|------|
| Content-heavy screens (feed, timer, reading) | **True Black Base** | Primary app surfaces, OLED battery benefit, maximum contrast |
| System UI, settings, forms | **Layered Near-Black** | Where the surface hierarchy needs to communicate elevation (base/card/overlay) |
| Premium surfaces, overlays, modals | **Glass / Frosted** | iOS 26 Liquid Glass moments. Sheets, tab bar backdrop, navigation bar over content |

### 5.5 Dark Mode Decision Tree

```
Designing a surface in Dark Mode?
├── OLED content screen (media, reading, timer, feed)?
│   └── True Black (#000) base
├── Settings, form, or utility screen?
│   └── Layered Near-Black (#111 base / #1C1C1E cards / #2C2C2E overlays)
└── Overlay, sheet, tab bar, or nav bar?
    └── Glass / Frosted (`.thinMaterial` or `.ultraThinMaterial`)
```

### 5.6 Accent Color — HIGH CONFLICT RESOLUTION

Three accent philosophies selected — these are genuinely opposed. CP 6.4.1 default is CTA-Only Restraint; Expressive Accent Spread is its opposite. Reconciliation requires strict context rules.

| Philosophy | When to Apply | Surfaces Allowed |
|------------|---------------|------------------|
| **CTA-Only Restraint** (default) | 90%+ of the app — productivity screens, data views, settings, lists | Primary CTA button. Active tab indicator. Selection state. Nothing else. |
| **Semantic Accent System** | When multiple functional states need visual distinction — e.g., progress bars, charts, success/error | CTAs + active states + progress + selection + charts. Secondary accent for success/error per CP colors. |
| **Expressive Accent Spread** | Onboarding screens, marketing/hero surfaces, celebration moments ONLY | Section backgrounds, icon fills, gradient surfaces. Never on utility/content screens. |

### 5.7 Accent Decision Tree

```
Applying accent color?
├── Is this a utility/productivity/content screen?
│   └── YES → CTA-Only Restraint (single accent point)
├── Does this screen need multiple functional states visually distinguished?
│   └── YES → Semantic System (CTA + states + chart data + progress)
└── Is this an onboarding, celebration, or marketing moment?
    └── YES → Expressive Spread is permitted — but document why
```

**Explicit violation examples:**
- ❌ Accent gradient on a session row card → CTA-Only wins for content screens
- ❌ Accent color fills on settings list icons → CTA-Only wins for utility
- ✅ Accent gradient behind the onboarding hero illustration → Expressive is permitted for onboarding
- ✅ Accent color on progress bar in the Stats tab → Semantic is permitted for functional distinction

See §15 for the full CP audit of this reconciliation.

## §6. TYPOGRAPHY & NUMERIC DISPLAY

### 6.1 Heading Tracking

**Tight Tracking on Headings** — single decision, no conflict.

```swift
Text("This Week")
    .font(.largeTitle.bold())
    .tracking(-1.0)  // -0.03em at ~34pt = ~-1pt

Text("Focus Time")
    .font(.title.bold())
    .tracking(-0.8)  // -0.03em at ~28pt
```

**Tracking scale:**
| Font size | Tracking |
|-----------|----------|
| ≥34pt (largeTitle) | -1.0pt |
| 28pt (title) | -0.8pt |
| 22pt (title2) | -0.5pt |
| 20pt (title3) | -0.3pt |
| ≤17pt (body/headline) | 0 (system default) |

**Do not** apply tracking to body text, caption, or footnote. Tight tracking at small sizes reduces legibility.

### 6.2 Numeric Display — Context Map

Two numeric styles selected, each with a distinct role:

| Style | When to Use | Spec |
|-------|-------------|------|
| **Hero Number Display** | Dashboard primary metrics, "today's" stat, single headline number | 48–64pt, `.thin` or `.regular` weight, `.monospacedDigit()`. Small muted label below (caption, `.secondary`). |
| **Mixed-Weight Numerics** | Financial/precise values, detail readouts where significant digits matter | Integer part: bold/heavy. Decimal part: regular/light. Same size for both. Monospaced digit. |

### 6.3 Numeric Display Decision Tree

```
Displaying a number?
├── Is this the single primary metric on screen (hero)?
│   └── Hero Number Display (48-64pt thin)
├── Does the number have significant decimal precision?
│   └── Mixed-Weight (bold integer + regular decimal)
├── Is it inline with other content (row value, chart annotation)?
│   └── Standard font + `.monospacedDigit()`
└── Is it changing frequently (timer, counter)?
    └── `.monospacedDigit()` — always, regardless of style
```

### 6.4 Hero Number SwiftUI

```swift
struct HeroMetric: View {
    let value: String
    let label: String

    var body: some View {
        VStack(spacing: 4) {
            Text(value)
                .font(.system(size: 56, weight: .thin, design: .default))
                .monospacedDigit()
                .tracking(-1.5)
                .foregroundStyle(.primary)
            Text(label)
                .font(.caption)
                .foregroundStyle(.secondary)
                .textCase(.uppercase)
                .tracking(0.5)
        }
    }
}
```

### 6.5 Mixed-Weight SwiftUI

```swift
struct MixedWeightNumber: View {
    let integer: String   // "$1,234"
    let decimal: String   // ".56"

    var body: some View {
        HStack(alignment: .firstTextBaseline, spacing: 0) {
            Text(integer)
                .font(.title.weight(.bold))
                .monospacedDigit()
            Text(decimal)
                .font(.title.weight(.regular))
                .monospacedDigit()
                .foregroundStyle(.secondary)
        }
    }
}
```

## §7. FEEDBACK & MICRO-INTERACTIONS

### 7.1 Toast / Notification — Context Map

| Context | Pattern | Spec |
|---------|---------|------|
| General success/info (global) | **Bottom Pill / Snackbar** | Max 80% width, 36–40pt pill, 16pt above tab bar. Auto-dismiss 2.5s. Slide up + fade in. |
| Field-specific feedback (inline validation, row action success) | **Inline Context Toast** | Appears near triggering element (field, button). 28–32pt height. 2s dismissal. |

### 7.2 Haptic Feedback — Tiered

Two selections resolve as tiered intensity:

**Baseline: Key Moments Only**
- Destructive confirm: `.notification(.warning)`
- Success completion: `.notification(.success)`
- Errors: `.notification(.error)`
- NOTHING ELSE gets standard haptics

**Premium Layer: Custom CHHaptic Patterns**
Reserved for signature moments that warrant Core Haptics investment:
- Session completion (multi-tap waveform)
- Milestone/streak crossed (crescendo pattern)
- Scrubbing over a chart or audio (continuous texture)
- Threshold reach (stretch + snap pattern)

**Rule:** Use custom patterns only where a signature physical metaphor enhances the moment. If a standard `.notification` works, use that. Custom haptics are craft moments, not utility moments.

### 7.3 Haptic Decision Tree

```
Building an interaction — does it warrant haptic?
├── Is it destructive, success-confirming, or error?
│   └── YES → Standard UINotificationFeedbackGenerator
├── Is it a signature moment (completion, milestone, scrub)?
│   ├── Does a physical metaphor enhance it meaningfully?
│   │   └── YES → Custom CHHaptic pattern
│   └── NO → No haptic
├── Is it a selection change in a picker/segmented control?
│   └── `.selectionChanged()` (system generator)
└── Otherwise (tap, scroll, standard button press)
    └── NO HAPTIC (your Key Moments rule)
```

### 7.4 Tab Bar Icon Animation — Context Map

Four options selected — resolve by production investment tier:

| Tier | Animation | When to Use |
|------|-----------|-------------|
| Default (no investment) | **Instant State Swap** | Initial MVP builds. Any tab not worth animating. System-default behavior. |
| Standard craft | **Outline to Fill Morph** | App has a considered design system — most tabs should use this. 200ms ease-out. |
| Expressive moment | **Spring Bounce** | 1–2 signature tabs (e.g., "New" action, "Home"). Never all of them. |
| Signature tier | **Lottie / Rive Animated Icon** | Brand-defining tab (e.g., a compose button). Reserve for 1 tab max. |

### 7.5 Tab Bar Animation Decision Tree

```
Implementing a tab?
├── Is this a critical brand moment (compose, primary action)?
│   └── Lottie/Rive for that ONE tab
├── Does the tab have a natural "playful" identity (home, discover)?
│   └── Spring Bounce
├── Standard utility tab (settings, library, search)?
│   └── Outline → Fill Morph
└── Ultra-minimal build or prototype?
    └── Instant State Swap
```

**Cap:** At most one Lottie tab and one Spring Bounce tab per app. Rest are Morph or Instant.

### 7.6 Toggle & Switch — Context Map

Four toggle styles resolve by control type:

| Control Type | Pattern | When |
|--------------|---------|------|
| Binary on/off setting | **Native UISwitch** | Settings, preferences, anywhere iOS users expect UISwitch. Don't fight the platform. |
| Binary with craft moment | **Spring Stretch Thumb** | Custom toggle for a signature setting (mode selection, primary feature) |
| Multi-option (2–4 choices) | **Segmented Pill Slider** | Mode switching, view toggles, filter selection |
| Completion / task check | **Checkbox → Checkmark Morph** | To-do lists, task completion, step completion |

### 7.7 Toggle Decision Tree

```
Building a control?
├── Binary (on/off)?
│   ├── Standard setting in a settings list? → Native UISwitch
│   └── Feature/mode toggle with craft investment? → Spring Stretch Thumb
├── 2-4 mutually exclusive options?
│   └── Segmented Pill Slider
└── Complete/incomplete task?
    └── Checkbox → Checkmark Morph
```

**Rule:** A screen should have at most ONE Spring Stretch Thumb toggle. Standard settings use UISwitch. Don't pepper custom toggles where users expect the system control.

## §8. ONBOARDING SYSTEM

Your note: *"I like each based on use case."* This codifies the use cases.

### 8.1 Onboarding Structure — Use Case Map

| App Type | Structure | Rationale |
|----------|-----------|-----------|
| Productivity / utility (Notion, Linear) | **Value-First (Show Don't Tell)** | Users want to try, not read. Drop them in with pre-filled data. |
| Complex workflow (accounting, research tools) | **Progressive Disclosure Steps** | Needs explicit education. 3–5 screens, skip always available. |
| Consumer / habit-forming (Duolingo-style) | **Interactive Tutorial** | First action = first win. Dopamine before account creation. |
| Personalized experience (meditation, fitness) | **Personalization Quiz** | Sets goals before launch. Commitment + tailoring upfront. |

### 8.2 Onboarding Decision Tree

```
Designing onboarding?
├── Is the app's value obvious from using it?
│   └── YES → Value-First (skip, pre-fill, go)
├── Does the app require user goals/preferences to function well?
│   └── YES → Personalization Quiz (3-7 questions)
├── Is there a specific first action that creates delight?
│   └── YES → Interactive Tutorial (first-win onboarding)
└── Does the app have non-obvious concepts requiring explanation?
    └── YES → Progressive Disclosure (3-5 screens)
```

### 8.3 Onboarding Progress — Your Note Applied

Your verbatim note: *"I like simplicity. Step counter is preferred for setup. Linear progress bar for progress as part of flow within app. Not used preference but initial feeling."*

Translation:

| Context | Indicator | Rationale |
|---------|-----------|-----------|
| Setup / onboarding flow (5+ steps) | **Step Counter Text** | "Step 2 of 5" — explicit, scannable |
| In-app progress (lesson, session, multi-step task) | **Linear Progress Bar** | Continuous fill, motivating pull |
| Very short flow (1–2 screens) | **No Indicator** | Nothing to indicate |

**Flagged:** You noted this is "initial feeling" — the Linear Progress Bar preference for in-app flow should be revalidated against a real flow before being treated as final.

### 8.4 Onboarding Animation — Your Notes Applied

Your verbatim notes:

> "Staggered element entry is ok if slower and smoother."
> "Morphing shape is super cool and shows care and intention."
> "Lottie scene animation ok on apps where want to minimize distraction but have some style."
> "I think I like slide + parallax but can't see it — it's not visible in design."

Translation:

| Animation | Status | Rule |
|-----------|--------|------|
| **Morphing Shape Transitions** | Premium signature | Use on flagship onboarding where "care and intention" is the brand message. High effort — plan for it. |
| **Staggered Element Entry** | Default, with condition | Slower than default (80–100ms stagger instead of 60ms). Smooth easing (`.easeOut`, not spring). |
| **Lottie Scene Animations** | Restrained style apps | Reserve for apps that "want to minimize distraction but have some style." Don't use for utility apps. |
| **Slide + Parallax** | 🟡 Tentative — validate in build | Cannot finalize until you see it in your design system. Build a prototype. |

### 8.5 Onboarding Animation Decision Tree

```
Choosing onboarding animation?
├── Is this a flagship/signature product launch moment?
│   └── Morphing Shape Transitions
├── Is the app intentionally understated/editorial?
│   └── Lottie Scene (restrained style)
├── Is this a prototype or standard build?
│   └── Staggered Element Entry (80-100ms, smooth)
└── Want depth without shape morphing?
    └── Slide + Parallax — BUT prototype first before committing
```

## §10. DELIGHT & CELEBRATION

### 10.1 Celebration — Your Note Applied

Your verbatim note: *"Full screen takeover can be ok for major achievements but needs to be more refined. My selected options for most use cases."*

Translation:

| Achievement Level | Pattern | Rule |
|-------------------|---------|------|
| Standard completion (task done, session saved) | **Checkmark Morph + Ripple** | Most cases. Subtle, satisfying. |
| Progress increment (XP, score, points) | **Score Tick + Glow** | Number counts up, soft glow pulse. |
| Major milestone (streak 100, big unlock) | **Refined Full-Screen Takeover** | Rare. Must be restrained — no confetti storm. Plan these moments specifically. |

### 10.2 Major Milestone Criteria

A full-screen celebration is warranted only when:
1. The moment is rare (≤1/month for typical user)
2. The user explicitly worked toward it (not an algorithmic surprise)
3. The celebration is restrained (one hero element + one supporting element, not a screen of confetti)

### 10.3 Splash Screen — Investment Tier Map

| Tier | Pattern | Use When |
|------|---------|----------|
| Fast / utility | **Logo Fade In/Out** | Every utility app. Default. |
| Craft signal | **Logo Draw / Assemble** | App where "designed with care" is part of the brand |
| Signature | **Splash Morphs Into UI** | App where launch itself is part of the product identity |
| Immersive | **Ambient Particle / Mesh** | Meditation, premium content, atmospheric apps only |

### 10.4 Splash Decision Tree

```
Designing splash?
├── Utility or productivity app?
│   └── Logo Fade In/Out
├── Brand cares about craft perception?
│   └── Logo Draw/Assemble
├── App launch IS part of the identity (premium content, meditation)?
│   └── Ambient Particle/Mesh OR Splash Morphs Into UI
└── When in doubt?
    └── Logo Fade In/Out (fastest, safest)
```

### 10.5 Scroll Physics — Context Map

Your note: *"I can't see sticky section headers or parallax background but I think I'd like it."*

| Pattern | Status | Use |

| **Snap-to-Card Paging** | Decided | Horizontal card carousels, one-card-at-a-time views (App Store discover, stories) |
| **Sticky Section Headers** | 🟡 Tentative — validate in build | Long lists with logical sections (contacts, grouped data). Test before committing. |
| **Parallax Background** | 🟡 Tentative — validate in build | Hero sections, profile headers, editorial content. Test before committing. |

## §11. LOADING & EMPTY STATES

### 11.1 Skeleton Loading — Context Map

Two styles selected — they serve different moods:

| Style | When | Context |
|-------|------|---------|
| **Shimmer Left-to-Right** | Content-rich screens (feed, search results, list of cards) | Users recognize it as "something's loading fast." Best for non-productivity screens. |
| **Pulse Fade** | Focus, meditation, productivity apps where shimmer would feel jittery | Calmer, less attention-grabbing. Use where the app's mood is calm. |

### 11.2 Skeleton Decision Tree

```
Choosing skeleton style?
├── Is this a productivity/focus/meditation app?
│   └── Pulse Fade (calmer)
├── Is this a content/feed/social app?
│   └── Shimmer Left-to-Right (familiar)
└── Is this a single critical load (<1s expected)?
    └── No skeleton — brief spinner or nothing
```

### 11.3 Empty State — Context Map

Two opposing styles selected — resolve by app tone:

| Style | When | Context |
|-------|------|---------|
| **Custom Illustration** | Consumer, playful, brand-driven apps | Onboarding moments, empty-first-time states, celebration of blank slate |
| **Text Only (Ultra Minimal)** | Editorial, productivity, minimal design aesthetic apps | Task managers, reading apps, tool apps where imagery feels out of place |

### 11.4 Empty State Decision Tree

```
Designing empty state?
├── Is the app minimal/editorial (Linear, Things, Arc-style)?
│   └── Text Only (20pt title, sub, CTA)
├── Is the app consumer/playful/brand-expressive?
│   └── Custom Illustration + CTA
├── Is this a filtered-empty state (not first-time)?
│   └── Text Only always — no illustration for "no search results"
└── Is this a first-time onboarding empty state?
    └── Custom Illustration if brand warrants, Text Only if utility
```

### 11.5 Per CP 6.4.1 Principle 10

Regardless of style choice, every empty state must follow CP 6.4.1 context matching:
- First-time → Encouraging tone + setup CTA
- Search → Broaden query suggestion, neutral tone
- Filter → Reset filters CTA + total count, neutral tone
- All done → Celebratory tone + next step CTA

See the iOS v1.1 Patch §B.4 for full copy examples.

## §12. SEARCH PLACEMENT RULES

Three search patterns selected — they are mutually exclusive and context-gated.

### 12.1 Search Decision Tree

```
Where does search live?
├── Is search the primary way users find content (Twitter/X, Pinterest)?
│   └── Dedicated Search Tab (magnifying glass in tab bar)
├── Is search ALWAYS needed on this screen (library, document list, feed)?
│   └── Sticky Top Bar (fixed top, 44-56pt permanent)
└── Is search useful but secondary (contacts, settings)?
    └── In Nav Bar, Scrolls Away (iOS HIG default)
```

### 12.2 Rule

One app uses ONE search pattern primarily. Mixing patterns across screens is acceptable only when the app type varies by tab (e.g., "Discover" tab uses dedicated search, "Library" tab uses in-nav-bar).

## §13. OPEN QUESTIONS (DECISION BACKLOG)

Eight categories remain undecided. Prioritized by blast radius — how many screens each decision affects.

### 13.1 Priority 1 — Every Screen Impact

These block the design system from being complete:

**1. Tap / Press Feedback**
- **Decision needed:** How does every tappable element respond?
- **Options to consider:** Scale-down press (CP mobile default — `active:scale-[0.98]`), ripple, opacity fade, subtle glow
- **Default if urgent:** Scale-down (`scaleEffect(0.98)` on press) matches CP mobile guidance

**2. Back Navigation Pattern**
- **Decision needed:** How do users go back within a NavigationStack?
- **Options:** System default (back chevron + swipe), custom back with screen name, bottom-aligned close button, gesture-only
- **Default if urgent:** System default — leverage iOS expectations

**3. Primary Button Shadow & Depth**
- **Decision needed:** Do primary CTAs have shadows, and at what depth?
- **Options:** Flat (no shadow), subtle lift (1-2pt shadow), medium depth (4pt), pronounced (8pt+)
- **Default if urgent:** Flat on dark surfaces, subtle lift (2pt shadow) on light

### 13.2 Priority 2 — Core System Components

**4. Tab Bar Style**
- **Decision needed:** Standard iOS tab bar, custom floating tab bar, pill tab bar, hidden-on-scroll?
- **Blocks:** L2 navigation hierarchy (CP Page Hierarchy §C)

**5. Active Tab Indicator**
- **Decision needed:** How is the active tab visually indicated?
- **Options:** Icon color + label fill, underline, background pill, dot above icon, top border
- **Blocks:** Depends on Tab Bar Style decision first

**6. Bottom Sheet Handle**
- **Decision needed:** Visible grabber handle? Invisible but draggable? None?
- **Options:** Standard grabber (`.presentationDragIndicator(.visible)`), custom handle, hidden but draggable, no drag
- **Blocks:** Every `.sheet` in the app

**7. Sheet Detent Behavior**
- **Decision needed:** How many detents? Transition between them?
- **Options:** Medium + Large (standard), Small + Medium + Large, Custom detents, Single detent
- **Blocks:** Every `.sheet`

### 13.3 Priority 3 — Context-Specific

**8. Swipe-to-Reveal Actions**
- **Decision needed:** Swipe direction conventions, haptic triggers, visual style of revealed actions
- **Options:** Right-swipe save + left-swipe delete (CP standard), custom mapping, swipe disabled
- **Default if urgent:** CP standard (right = positive, left = negative, 80pt threshold, haptic on trigger)

### 13.4 Recommended Decision Session

Decide these 8 in one focused session against actual screens from a current RossLabs project. Don't decide them in isolation.

## §15. CP 6.4.1 CONFLICT AUDIT

Flagging preferences that diverge from CP 6.4.1 defaults. These divergences are permitted by explicit context rules, but should be audited in review.

### 15.1 Accent Color Spread Conflict

**CP 6.4.1 Default (Principle 5 — Text Over Decoration):** Status = text color only. Accent appears only on single primary CTA.

**Preference:** Expressive Accent Spread selected alongside CTA-Only Restraint.

**Reconciliation:** §5.6 context rules — Expressive Spread is permitted only on onboarding, celebration, and marketing moments. Utility/content screens use CTA-Only. If an accent gradient appears on a content row background, that's a violation.

**Review checkpoint:** In design review, flag any accent color on a non-onboarding/non-celebration surface. Force justification.

### 15.2 Aurora / Mesh Gradient Conflict

**CP Principle 5 / Signal-to-Noise:** Decoration should aid comprehension, not add visual noise.

**Preference:** Mesh/Aurora gradient selected.

**Reconciliation:** §5.3 — one aurora gradient per screen maximum, reserved for hero surfaces (splash, onboarding hero, premium badge). Not allowed on content cards or utility surfaces.

**Audit flag:** Per your memory, Aurora themes have unresolved mobile degradation guidance. Test backdrop-filter blur performance on iPhone SE / iPhone 11 before any Aurora screen ships.

### 15.3 Lottie Scene Animations Conflict

**CP Principle 12 — Purposeful Motion:** Every animation must answer "what is this telling the user?" If the answer is "it looks nice," remove it.

**Preference:** Lottie onboarding animations selected.

**Reconciliation:** §8.4 — Lottie reserved for "apps that want to minimize distraction but have some style." Each Lottie animation must communicate a specific message (e.g., "this feature tracks your progress" — animate a progress concept). Decorative Lotties are rejected.

**Review checkpoint:** Before approving a Lottie, state in one sentence what the animation communicates. If you can't, cut it.

### 15.4 Multi-Card Card-Per-Row Conflict

**CP Principle 1 — Group, Don't Isolate:** Single border + dividers for related items.

**Preference:** Card Per Row selected.

**Reconciliation:** §4.3 — Card Per Row is allowed only when rows are genuinely independent entities. When rows form a logical group (settings, grouped transactions), Inset Hairline wins.

**Review checkpoint:** For every list using Card Per Row, ask: "Would the user scan these as one unit?" If yes, convert to Inset Hairline.

### 15.5 Progress Ring Rejection — CP Alignment

**Your note:** "I generally don't like progress rings unless it's a timer then it's ok and only one ring."

**CP alignment:** This is a direct Signal-to-Noise win. Multiple progress rings duplicate information with visual complexity. Your instinct is correct; the auto-apply rule P20 codifies it.

**No conflict — noted for completeness.**
