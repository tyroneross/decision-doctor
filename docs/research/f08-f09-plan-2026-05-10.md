## TL;DR

F-08 (AI-feasibility scoring) is a **1-day chunk**, mostly additive: one new engine stage, one schema field, one display helper, chip-color update across two UI files. F-09 (skill/plugin scaffold generator) is a **2-day chunk** that lands one new component (`ScaffoldViewer`), one new engine stage, a templating module, and a new mockup (v2-08). ## Architecture changes

### Engine pipeline — current vs proposed

```
CURRENT (lib/engine/orchestrator.ts)
─────────────────────────────────────
Stage 1 (LLM)  values            ─┐
                                  │
Stage 2        constraints  ←─────┤  sequential
                                  │
Stage 3        weights       ←────┤
                                  │
Stage 4        outranking    ←────┤
                                  │
Stage 5 (LLM)  ranking +     ←────┘
                workloadReducers


PROPOSED
─────────────────────────────────────
Stage 1 (LLM)  values            ─┐
                                  │  sequential
Stage 2        constraints  ←─────┤
                                  │
Stage 3        weights       ←────┘

Stage 4        outranking    ─┐
                              │   PARALLEL (Promise.all)
Stage 6 (LLM)  feasibility   ─┘   per F-08; both gated on Stage 3 output

Stage 5 (LLM)  ranking +
                workloadReducers
                                  ← consumes Stage 4 + Stage 6 outputs

Stage 7        scaffold      ←─── fires only if ≥1 reducer is "skill" or "plugin"
                                  per F-09; deterministic, no LLM call needed
                                  (templates are parameterized)
```

**Why parallel Stage 4 + Stage 6:** they share inputs (weights from Stage 3, candidate set from Stage 2) and produce independent outputs. The PRD's composable-engine must-have already mandates "parallelize stages where dependency graph allows" (added in commit `93570d7`).

**Estimated latency impact:**
- Stage 6 feasibility classification (LLM): ~1.0s — absorbed by Stage 4 running in parallel (Stage 4 deterministic, ~50ms, so wall-clock = LLM time)
- Stage 7 scaffold generation (deterministic, template-based): ~50ms when triggered
- Net p95 increase over current build: **+0.05–0.3s** depending on parallelism efficiency
- New p95 estimate: ~3.5–4.5s (was 2.8s) — well within the relaxed ≤8s target

### Data model — schema diff

`shared/schema.ts` — extend `WorkloadReducerSchema`:

```ts
export const ScaffoldFileSchema = z.object({
  path: z.string(),                 // "SKILL.md", "plugin.json", "commands/run.md"
  content: z.string(),              // full file body, paste-ready
  language: z.enum(["markdown", "json", "yaml", "bash", "typescript"]),
});

export const ScaffoldSchema = z.object({
  targets: z.array(z.enum(["claude-code-skill", "claude-code-plugin", "codex-skill", "codex-plugin"])),
  files: z.array(ScaffoldFileSchema).min(1),
});

export const WorkloadReducerSchema = z.object({
  // existing fields preserved
  type: z.enum(["prompt", "skill", "plugin", "mcp_tool", "playbook"]),
  title: z.string(),
  description: z.string(),
  artifact: z.object({ /* unchanged */ }),
  automationLevel: z.enum([...]),
  coverage: z.enum([...]),
  permission_tier: z.enum([...]),

  // NEW per F-08:
  aiFeasibility: z.enum(["skill", "plugin", "agent", "human"]),
  feasibilityRationale: z.string().min(1).max(280),   // 1-sentence "why this tier"
  impactScore: z.number().min(0).max(100),            // hrs/wk × repeatability × stress
  feasibilityScore: z.number().min(0).max(100),       // composite from Stage 6
  combinedScore: z.number().min(0).max(100),          // impact × feasibility (Stage 5 uses to rank)

  // NEW per F-09 (only present when aiFeasibility ∈ {"skill","plugin"}):
  scaffold: ScaffoldSchema.optional(),
});
```

**No DB migration.** Reducers persist as JSONB in `decisions.workload_reducers`; the schema just gets richer over time. Existing rows without these fields render with sane defaults (chip says "Human review" / scaffold hidden).

### Display helper

`lib/decision-display.ts` extends with:

```ts
const FEASIBILITY_STYLES = {
  skill:  { label: "Skill",       icon: "🛠️", tone: "var(--skill)", bg: "var(--skill-bg)" },
  plugin: { label: "Plugin",      icon: "🧩", tone: "var(--plum)",  bg: "var(--plum-bg)" },
  agent:  { label: "Agent",       icon: "🤖", tone: "var(--cap)",   bg: "var(--cap-bg)" },
  human:  { label: "Human review", icon: "👤", tone: "var(--ink-500)", bg: "var(--cream-2)" },
};

export function feasibilityFor(aiFeasibility: AiFeasibility) {
  return FEASIBILITY_STYLES[aiFeasibility];
}
```

Mirrors the existing `categoryFor()` pattern in the same file.

### API & routes

- `POST /api/decisions` response shape **extends additively** — no breaking changes for clients reading the response.
- Decision: ship the scaffold **inline in the response body** (under each reducer's `scaffold` field). The largest realistic scaffold is ~15kb gzipped; the engine response already runs ~30kb. Under the practical Vercel response limit (4.5MB). If real-world scaffolds grow past 50kb total, promote to a lazy endpoint:
  - `GET /api/decisions/[id]/reducer/[index]/scaffold` returning just the scaffold object.

## UI surfaces

### F-08 surfaces — already in mockups, need 4-tier color update

The v2-06 history-list and v2-07 detail mockups already render an "AI: high / med / low" chip on every reducer card. The chip exists; F-08 changes its **content and color**:

| Current (3-tier impressionistic) | New per F-08 (4-tier prescriptive) |
|---|---|
| `AI: high` → green | `🛠️ Skill` → teal — the on-ramp; safest, ship today |
| `AI: med` → sun | `🧩 Plugin` → plum — more capable; multi-step |
| `AI: low` → rose | `🤖 Agent` → coral — advanced; sustained automation |
| (n/a) | `👤 Human review` → muted ink — AI shouldn't own (trust/regulated) |

**Why 4-tier prescriptive beats 3-tier impressionistic:** the chip's *job* is to tell the user *how to ship*, not whether to try. "Plugin" prompts a different action than "Skill." The 3-tier was useful for the mockup but undersells the product's actual output.

**Files touched in v2-06/v2-07:** none — they're reference mockups; the implementation code is where the change lands.

### F-08 new surface — Ranked drains panel

The detail page needs a **ranked-drains sidebar** showing every reducer the engine considered, sorted by `combinedScore` (impact × feasibility), with the chosen one expanded. This is currently buried inside the "what changes" card on v2-07; promoting it serves the new product story (the *ranking* is the IP).

**Spec:**
- Replaces the right column on v2-07 detail (currently three MECE cards) with two columns:
  - Left: the existing "the skill we built" hero
  - Right (NEW): "All drains ranked" — list of reducers with feasibility chip + combined score, top one auto-expanded, others collapsed
- Maintains the Pyramid: hero on top, ranked list = the supporting evidence, math under disclosure

### F-09 surfaces — new `ScaffoldViewer` component

**Component pattern** — research-grounded:
- **PatternFly Clipboard Copy** + **Cloudscape Copy-to-Clipboard** — single-file copy with transient "Copied ✓" feedback, focus-trapped accessible.
- **shadcn / ScaffoldHub copy-paste** — multi-file scaffold viewer using a tabbed layout: files as left-rail tabs, code preview as right pane.
- **Visual Studio 2026 HTML-clipboard** — preserve syntax highlighting through the clipboard.

**`ScaffoldViewer` spec (new mockup: `v2-08-scaffold-viewer.html`):**

```
Trigger: green "🛠️ Skill ready" card on v2-07 detail
         → "Open scaffold" CTA → drawer (desktop) / sheet (mobile)

Layout (drawer, ~640px wide):

┌──────────────────────────────────────────────────────────────────┐
│ Scaffold · Insurance pre-auth letter skill              ✕ Close  │
│ ┌──────────┐  ┌──────────┐                                       │
│ │Claude Code│  │  Codex   │   ← target tabs                      │
│ └──────────┘  └──────────┘                                       │
├──────────────────────────────────────────────────────────────────┤
│  📁 Files            │ ─── SKILL.md ──────────────────  📋 Copy ─│
│ ▸ SKILL.md  (active) │ ---                                       │
│   AGENTS.md          │ name: pre-auth-letter                     │
│                      │ description: Drafts insurance pre-auth... │
│                      │ ---                                       │
│                      │                                           │
│                      │ # Pre-auth Letter Skill                   │
│                      │ ...                                       │
├──────────────────────────────────────────────────────────────────┤
│  📥 Copy all  ·  💾 Download as ZIP  ·  ▶️ Try in Claude Code    │
└──────────────────────────────────────────────────────────────────┘
```

**Calm Precision compliance:**
- §1 Common Region: single border around the drawer; files separated by tabs (not individual borders).
- §2 Fitts: per-file copy button is `h-9 px-3` (≥36px touch). "Copy all" / "Download" are full-width on mobile.
- §3 Hick: viewer is collapsed by default; opens only on user trigger.
- §4 Signal-to-noise: "Copied ✓" is teal text only, no green pill. Failure is rose text.
- §5 Content ≥ chrome: code preview takes >70% of the drawer's content area.
- §6 Cognitive load: max ~5 files per scaffold (skill = 2 files; plugin = up to ~6); if exceeded, add a search/filter.

**Accessibility:**
- Focus-trap inside the drawer per WAI-ARIA dialog pattern.
- Tabs use the WAI-ARIA tabs pattern (`role="tablist"`, arrow-key navigation).
- Copy button announces success via aria-live region.

## Build-loop dispatch plan

### Chunk A — F-08 AI-feasibility scoring (~1 day)

**Files (7):**
1. `shared/schema.ts` — add `aiFeasibility`, `feasibilityRationale`, `impactScore`, `feasibilityScore`, `combinedScore` to `WorkloadReducerSchema`
2. `lib/engine/stage6-feasibility.ts` — NEW LLM classifier stage; ~80 lines
3. `lib/engine/orchestrator.ts` — `Promise.all([stage4(), stage6()])` after Stage 3
4. `lib/engine/stage5-ranking.ts` — consume `combinedScore` from Stage 6; rank reducers by it

6. `components/recommendation/RecommendationView.tsx` — render new chip, add ranked-drains sidebar

**Test:** `tests/feasibility.test.ts` (T-11) — assert each reducer has feasibility ∈ enum, asserts deterministic tiebreak (same input → same rank), asserts UI renders the chip.

**Mockup work:** annotate v2-07 with 4-tier chip colors (in-place edit).

**Risk:** Stage 6 LLM prompt needs careful design — `aiFeasibility` should be deterministic for the same input. Use `temperature: 0`, structured output, and a small classification rubric in the system prompt.

### Chunk B — F-09 Scaffold generator (~2 days)

**Prerequisite:** Chunk A merged.

**Files (10):**
1. `shared/schema.ts` — add `ScaffoldFileSchema`, `ScaffoldSchema`, attach `scaffold` to `WorkloadReducerSchema`
2. `lib/scaffold-generator.ts` — NEW; main entry: `generateScaffold(reducer): Scaffold | null`

4. `lib/scaffold-templates/plugin.template.json` — NEW
5. `lib/scaffold-templates/agents-block.template.md` — NEW (Codex AGENTS.md block format)
6. `lib/engine/stage7-scaffold.ts` — NEW; iterates reducers, calls `generateScaffold()` for skill/plugin classified ones
7. `lib/engine/orchestrator.ts` — append Stage 7 after Stage 5
8. `components/scaffold/ScaffoldViewer.tsx` — NEW drawer component
9. `components/scaffold/CodeBlock.tsx` — NEW syntax-highlighted code block with copy
10. `components/recommendation/RecommendationView.tsx` — wire "Open scaffold" CTA on the Skill-ready card

**Test:** `tests/scaffold.test.ts` (T-12):
- For ≥1 `"skill"` reducer: emitted SKILL.md parses (frontmatter via `gray-matter`, body non-empty, ≤200 lines).
- For ≥1 `"plugin"` reducer: emitted `plugin.json` validates against Claude Code's plugin schema (fetch the canonical schema from the official docs); minimal directory layout exists.
- For both targets: copy-to-clipboard works in JSDOM (mock `navigator.clipboard`).

**Mockup work:** write `v2-08-scaffold-viewer.html` per the spec above.

**Risks:**
1. **Codex `AGENTS.md` format** — verify the latest spec via Context7 or OpenAI docs before locking the template. Format has evolved; cite source in the template file.
2. **Plugin scaffold completeness** — Claude Code's plugin format includes optional MCP server config, hooks, etc. v1 ships the minimal valid plugin (manifest + one command); v1.1 can expand to richer scaffolds.

## Risks & open questions

| # | Risk | Mitigation |
|---|---|---|
| 1 | Codex `AGENTS.md` format evolves | Fetch latest spec via Context7 before Chunk B; cite source in the template file header; pin to a dated version. |
| 2 | Scaffold inflates response size beyond practical | Default to inline; promote to lazy `/api/decisions/[id]/reducer/[i]/scaffold` if avg payload > 50kb. |
| 3 | Stage 6 classifier non-determinism | `temperature: 0`, structured-output JSON, rubric in system prompt; test asserts deterministic tiebreak. |
| 4 | F-09 scaffolds drift from actual plugin specs | Schedule a quarterly check: re-validate emitted plugin.json against the latest Claude Code Zod schema; bump the template if breaking. |
| 5 | Drawer URL sharing | v1 ships as in-page drawer (not URL-addressable). If user demand surfaces, promote to `/app/decisions/[id]/scaffold/[reducer]` in v1.1. |

## Recommendation

**Dispatch Chunk A only as the next build-loop run.** Reasons:
- F-08 is independently shippable and immediately raises engine-output information density.
- F-09 has a higher unknown surface (Codex spec, scaffold completeness) — best landed with a focused build-loop pass and its own design north star (v2-08 mockup) rather than bundled.
- Two-day buildathon window (round 1 due 2026-05-12) realistically lands F-08 cleanly; F-09 lands round 2.

If you'd rather bundle, the build-loop can take both chunks in one run — adds risk but technically clean.
