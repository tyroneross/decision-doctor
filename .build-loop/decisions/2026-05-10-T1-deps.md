# 2026-05-10 — Tranche 1 dependency-friction decisions

## better-auth 1.6.10 wants drizzle-orm@^0.45.2; we have 0.36.4

**Options considered:**
- A. Bump drizzle-orm to 0.45 + drizzle-kit compatible release. Risk: schema-API
  breaking changes (pgTable signature, indices, sql template), shared Neon DB
  schema is already migrated; drizzle 0.45 also requires zod 4 in some types.
- B. Pin better-auth to a 1.x release that works with drizzle 0.36 (1.0.x line).
  Risk: missing magic-link flow polish.
- C. Keep current install — peer-warning only, runtime should work because
  better-auth's drizzle adapter only uses `pgTable`, `eq`, `and`, primitive
  query builder primitives that are stable across 0.36 → 0.45.

**Pick: C (keep current install).** Lowest risk. Branch B is local-only;
runtime errors would surface in our test pass and be diagnosed before push.
If a real runtime break occurs in Tranche 2 wiring, fall back to A
(bump drizzle-orm to 0.45) — the schema we already pushed is simple enough
that the API surface used is stable.

## better-call 1.3.5 wants zod@^4.0.0; we have zod 3.25.76

**Pick: ignore the warning.** better-call is a transitive dep of better-auth.
Test in Tranche 2; if zod 4-only API is hit at runtime, install zod 4 alongside
zod 3 via a path-alias OR pin better-auth to a release predating better-call 1.3.

## RLS in schema.ts via pgPolicy() — defer to Tranche 1.5

Drizzle 0.36 supports `pgPolicy()` but the schema is already pushed and the
0001_enable_rls.sql is idempotent. Add a `db:rls` npm script that re-applies
the SQL after every `db:push` and chain it. Do NOT migrate the policies into
schema.ts yet — risk of churn against shared Neon DB during Branch A's run.
